Chapter 3 · Processes

תהליכים

איך מעבד אחד מריץ "הכל בבת אחת" בלי לאבד שליטה, ואיך יוצרים תהליכים בפועל. השאלות על fork הן מהשכיחות במבחן.

מהו תהליך

הגדרה

תהליך = תוכנית רצה. תוכנית היא קוד ונתונים סטטיים על הדיסק; תהליך הוא מופע דינמי שלה. יכולים להיות כמה תהליכים של אותה תוכנית במקביל.

לכל תהליך מרחב כתובות משלו, עם ארבעה אזורים:

אזורמה יש בובין שני תהליכים של אותה תוכנית
Textפקודות התוכנית (קוד)אותו גודל, אותו תוכן
Dataמשתנים גלובליים וקבועיםאותו גודל, תוכן שונה
Heapהקצאה דינמית (malloc), גדל כלפי מטהגודל ותוכן שונים
Stackמשתנים מקומיים, ארגומנטים, קריאות פונקציה, גדל כלפי מעלהגודל ותוכן שונים

טבלת התהליכים ו-PCB

מערכת ההפעלה מחזיקה טבלת תהליכים עם רשומה לכל תהליך פעיל – Process Control Block (PCB):

  • מזהה תהליך (PID)
  • מצב (state)
  • תהליכים קשורים (הורה)
  • הקשר מעבד – אוגרים, שנשמרים כשהתהליך מושהה
  • מיקומי זיכרון
  • קבצים פתוחים

וירטואליזציה של המעבד: Limited Direct Execution

Time sharing: מריצים תהליך, עוצרים, מריצים אחר, וחוזר חלילה. שני אתגרים: ביצועים (בלי תקורה מוגזמת) ושליטה (מערכת ההפעלה חייבת להישאר בשליטה על המעבד).

Direct Execution – פשוט להריץ את main() ישירות על המעבד – מהיר, אבל יש בו שתי בעיות:

בעיהפתרון
1. לתהליך יש גישה מלאה לחומרהרמות הרשאה בחומרה: user mode מוגבל (למשל בלי I/O), kernel mode בלי הגבלות. פעולה רגישה ← system call
2. אי אפשר לעצור תהליך שרץTimer interrupt – הגישה ה-preemptive (בהמשך)

טבעות ההרשאה במעבדי x86: Ring 0 לקרנל, Ring 3 לאפליקציות (1–2 לדרייברים, בפועל כמעט לא בשימוש).

קריאת מערכת – צעד אחר צעד

לכל קריאת מערכת יש מספר ידוע. היא חשופה כ-API מבוקר לפעולות רגישות.

#תהליך (user mode)חומרהמערכת הפעלה (kernel mode)
1ספריית C שמה ארגומנטים ומספר syscall, ומבצעת trap
2שומרת אוגרים ל-kernel stack, עוברת ל-kernel mode, קופצת ל-handler
3מבצעת את הקריאה, ואז return-from-trap
4משחזרת אוגרים, חוזרת ל-user mode
5פורסת את ערך ההחזרה וממשיכה

Context Switch

כשתהליך רץ, מערכת ההפעלה – בהגדרה – לא רצה. אז איך היא לוקחת חזרה את המעבד?

גישהאיךבעיה
Cooperativeסומכים על התהליך שימסור שליטה: syscall, page fault, שגיאה, או קריאת yield מפורשתתהליך באגי, זדוני או איטי (לולאה אינסופית) תוקע את המחשב
Preemptiveבאתחול מערכת ההפעלה מפעילה טיימר חומרה; כל כמה מילישניות הוא שולח interrupt והקרנל חוזר לשליטה— הפתרון בפועל

התעלול: הקרנל שומר את האוגרים של A ב-PCB שלו וטוען ל-kernel stack את אלה של B. לכן כשהחומרה מבצעת return-from-trap ומשחזרת אוגרים, היא "חוזרת" לתהליך B ולא ל-A.

מחזור החיים של תהליך

ה-API של תהליכים: fork, wait, exec

ה-API של מערכת ההפעלה הוא קריאות המערכת. כדי לא לכתוב קוד מחדש לכל מערכת יש תקן POSIX, וספריות מסתירות פרטים (printf הוא עטיפה ל-write). התהליכים יוצרים עץ: לכל תהליך הורה, והשורש הוא init (PID 1).

pid_t fork(void);
מה
יוצר תהליך חדש – עותק כמעט מדויק של ההורה (עטיפה ל-clone).
זהה
זיכרון (עותק!), נקודת ביצוע – שניהם ממשיכים מהשורה שאחרי fork, קבצים פתוחים.
שונה
PID וערך ההחזרה.
מחזיר
להורה: ה-PID של הילד (> 0). לילד: 0 – זה לא PID, רק סימון. בכישלון: -1.
יעילות
Copy-on-write: הדפים מועתקים בפועל רק כשמישהו כותב אליהם.
pid_t wait(int *status); pid_t waitpid(pid_t pid, int *status, int options);
מה
חוסם עד שילד כלשהו מסתיים (waitpid – ילד ספציפי). מחזיר את ה-PID שלו, או -1 אם אין ילדים.
מגבלות
רק ילדים ישירים – לא נכד, לא אח, לא הורה. אם ילד כבר הסתיים (זומבי), wait חוזר מיד ואוסף אותו.
לכולם
while (wait(NULL) != -1);
int execvp(const char *file, char *const argv[]);
מה
מריץ קוד של תוכנית אחרת בתוך אותו תהליך – דורס את זיכרון התהליך וקורא ל-main() שלה.
אין תהליך חדש
ה-PID נשאר זהה.
חוזר?
exec שהצליח לעולם לא חוזר. כל שורה אחריו רצה רק אם הוא נכשל.
argv
מערך שמתחיל בשם התוכנית ומסתיים ב-NULL.
int main() {
    pid_t pid1 = getpid();     // 5
    pid_t pid2 = fork();       // parent: 6 | child: 0
    printf("%d\n", getpid());  // parent: 5 | child: 6
    printf("%d\n", pid1);      // both: 5  (copied before fork)
    printf("%d\n", pid2);      // parent: 6 | child: 0
}
מה הקרנל עושה בזמן fork
  1. התהליך מבצע trap – עובר ל-kernel mode ושומר את האוגרים שלו.
  2. הקרנל מקצה PID חדש ורשומת PCB חדשה בטבלת התהליכים.
  3. הוא מעתיק לילד את מרחב הכתובות של ההורה, את האוגרים ואת טבלת הקבצים הפתוחים. בפועל ההעתקה עצלה, בשיטת copy-on-write.
  4. הוא כותב ערך החזרה שונה לכל אחד: ה-PID של הילד אצל ההורה, ו-0 אצל הילד.
  5. שני התהליכים במצב "מוכן", ומי ירוץ קודם זו החלטה של המתזמן.

בהרצות היבשות לוחצים הבא (או חץ שמאלה במקלדת) ורואים צעד אחר צעד: איפה כל תהליך נמצא בקוד, את טבלת התהליכים עם המשתנים והמצב של כל אחד, את עץ התהליכים, ואת הפלט – צבוע לפי התהליך שהדפיס אותו. הסדר שמוצג הוא הרצה אחת אפשרית.

סדר הביצוע לא מובטח

אחרי fork אין שום הבטחה מי ירוץ קודם – זה תלוי במתזמן. הדרך להפוך את הפלט לדטרמיניסטי היא wait.

דוגמה: לזיכרון של הילד יש עותק משלו
int x = 0;
int rc = fork();
if (rc) wait(NULL);   // parent: waits for the child
else    x += 3;       // child: changes only its own copy
printf("%d\n", x);

הפלט תמיד 3 ואחריו 0. בלי ה-wait (עם sleep(5) במקומו) הפלט "בדרך כלל" 3 ואז 0, אבל זה תלוי בתזמון. וגרסה שבה רק ההורה מדפיס אחרי sleep תדפיס 0 – השינוי של הילד לא נראה להורה.

שלושה דפוסים של wait

מצבקריאהמה קורה
ילד אחדwait(NULL)ההורה חסום עד שהילד מסתיים, ואז ממשיך.
כמה ילדים – לחכות לכולםwhile (wait(NULL) != -1);כל קריאה חוזרת כשילד כלשהו מסתיים. כשלא נשארו ילדים, wait מחזיר -1 והלולאה נגמרת.
ילד מסויםwaitpid(cpid, NULL, 0)ההורה מחכה דווקא ל-cpid. אם ילד אחר מסתיים קודם – ההורה ממשיך לחכות.

לכל הדפוסים אותן מגבלות: רק ילדים ישירים, ואם הילד כבר הסתיים (זומבי) – הקריאה חוזרת מיד ואוספת אותו.

סטטוס היציאה של הילד

במקום NULL אפשר להעביר מצביע ל-int, ו-wait ימלא בו מידע על איך הילד הסתיים. את המידע מפענחים עם מאקרואים:

מאקרומה בודק / מחזיר
WIFEXITED(status)האם הילד הסתיים כרגיל (חזר מ-main או קרא ל-exit)
WEXITSTATUS(status)קוד היציאה – הערך שהילד העביר ל-exit. תקף רק אם WIFEXITED אמת
WIFSIGNALED(status)האם הילד נהרג על ידי סיגנל
WTERMSIG(status)מספר הסיגנל שהרג אותו
pid_t pid = fork();
if (pid == 0) {
    printf("Child (PID: %d) running...\n", getpid());
    sleep(1);
    exit(42);                       // send exit code 42 to the parent
}
int status;
wait(&status);                     // wait and capture the termination status
if (WIFEXITED(status))
    printf("Child exited normally with code: %d\n", WEXITSTATUS(status));
else if (WIFSIGNALED(status))
    printf("Child killed by signal: %d\n", WTERMSIG(status));

בדקתי בהרצה: הפלט היה Child exited normally with code: 42. בהרצה נוספת שבה ההורה הרג את הילד עם SIGKILL התקבל Child killed by signal: 9.

exec עם ארגומנטים

התוכנית someprog:

void myfunc() { printf("(%d) myfunc\n", getpid()); }

int main(int argc, char *argv[]) {
    printf("my pid is %d\n", getpid());
    myfunc();
    char* args[4] = { "./myprog", "hello", "world", NULL };
    execvp(args[0], args);
    printf("this shouldn't print out");
}

והתוכנית myprog:

int main(int argc, char *argv[]) {
    printf("(%d) received %d args\n", getpid(), argc - 1);
    for (int i = 1; i < argc; ++i)
        printf("(%d)\t%d: %s\n", getpid(), i, argv[i]);
}

הפלט בהרצה אמיתית:

my pid is 3042
(3042) myfunc
(3042) received 2 args
(3042)	1: hello
(3042)	2: world

כל השורות עם אותו PID – exec לא יוצר תהליך. argc הוא 3 (שם התוכנית ועוד שני ארגומנטים), ולכן myprog מדווח על 2. השורה האחרונה של someprog לא מודפסת.

exec בשילוב fork – כך עובד ה-shell

int rc = fork();
if (rc < 0) { fprintf(stderr, "fork failed\n"); exit(1); }
else if (rc == 0) {                      // child
    char *args[] = { "wc", "-l", "exec.c", NULL };
    execvp(args[0], args);
    printf("this shouldn't print out\n"); // only if exec failed
} else {                                 // parent
    int rc_wait = wait(NULL);
    printf("I am parent of %d (rc_wait:%d) (pid:%d)\n", rc, rc_wait, getpid());
}
למה fork ו-exec נפרדים?

כי אפשר להריץ קוד אחרי fork ולפני exec ולשנות את הסביבה של התוכנית החדשה – למשל לסגור את stdout ולפתוח במקומו קובץ. כך ה-shell מממש > ו-| בלי שהתוכנית המורצת תדע בכלל.
